# Example: STM32G0B1 bootloader

The bootloader half of a reference integration for an STM32G0B1KEU6-class device (512 KB flash, dual bank, Cortex-M0+). It shows how
`fwu_boot_start` is wired to the STM32 flash port, how the application is validated and started, how the bootloader leaves a result for the
application in RAM, and how the flash ECC double-error NMI is handled.

**Scope and limits (read first)**

* **Bootloader only.** The application side of this integration is a product-specific project that is not part of this repository. For the
  application (session, link, transport) follow [`docs/INTEGRATION_GUIDE.md`](../../docs/INTEGRATION_GUIDE.md) and the C2000 application example,
  which shows the same core calls on a different MCU.
* **Not a complete project.** There is no startup file, system clock setup, HAL configuration or CubeMX project here. The files assume an
  STM32CubeIDE project for the STM32G0B1 that provides `main.h`, `stm32g0xx_hal_conf.h`, the HAL and CMSIS drivers, startup code and the
  vector table, and that calls the two entry points below. The ST linker script `bootloader/STM32G0B1KEUX_FLASH.ld` is included as
  generated by STM32CubeIDE with two edited `MEMORY` lines (see "Memory map").
* **Status:** the sources compile with GNU Arm 13.3.1 against the real ST HAL headers (`tests/target_builds/arm_gcc_compile_check.sh`, evidence
  [`arm_gcc_compile_check.txt`](../../docs/evidence/arm_gcc_compile_check.txt)); the flash port logic passes its PC stub tests; a firmware update
  whose bootloader used this code completed on a device (recorded host log, [`TEST_RESULTS.md`](../../docs/TEST_RESULTS.md) D5). Power-loss behaviour
  and the ECC/NMI path on silicon are not recorded.

## Files

| File | Purpose |
|---|---|
| `bootloader/boot_app.c`, `boot_app.h` | `boot_app_run()` (the bootloader's whole job; does not return) and `boot_app_nmi()` (call from `NMI_Handler`) |
| `bootloader/fwu_platform.h` | settings shared by bootloader and application: profile, board, product id, chunk size, memory map, and the RAM mailbox structure |
| `bootloader/STM32G0B1KEUX_FLASH.ld` | linker script (ST-generated header kept; third-party notice, see [`THIRD_PARTY_NOTICES.md`](../../THIRD_PARTY_NOTICES.md)) |

Dependencies not in this repository: STM32G0 HAL and CMSIS (STM32CubeG0), your clock/startup code, `main.h`.

## Flow (`boot_app_run`, `boot_app.c`)

1. Initialise the flash port (`fwu_flash_stm32g0_init_mcu`) and the software crypto port (`fwu_crypto_sw_init`). If either fails the decision stays STAY with
   reason `FWU_BOOT_REASON_CONFIG`.
2. Fill `fwu_boot_config_t` (policy from the profile, layout from the board plus the image limit, product id, work buffers, hooks) and call
   `fwu_boot_start`: this verifies and installs a pending update.
3. Encode the contract record (`fwu_boot_info_encode`) and write result and record into the RAM mailbox.
4. On `FWU_BOOT_JUMP_APP`: `jump_to_app()` - disable interrupts, stop SysTick, clear NVIC enable/pending bits and pending SysTick/PendSV,
   `HAL_RCC_DeInit`, set `VTOR` and `MSP`, re-enable interrupts, branch to the reset vector. Otherwise loop forever (no sleep, so a debugger can
   attach).

`app_valid` (hook): the application's initial stack pointer must lie in RAM and be 4-byte aligned, and the reset vector must be odd (Thumb) and lie in
the application region. `watchdog_arm` (hook, trial boots in SWAP mode only): starts the independent watchdog at about 4 s.

Add to your project:

```c
/* main.c, after HAL_Init() and SystemClock_Config() */
boot_app_run();            /* verify/apply a pending update, then jump to the application; does not return */

/* stm32g0xx_it.c */
void NMI_Handler(void) { boot_app_nmi(); }   /* returns after a flash ECC double error, otherwise resets */
```

## Memory map (from `fwu_platform.h` and the linker script)

| Region | Address | Notes |
|---|---|---|
| Bootloader | `0x08000000`, 36 KB (pages 0..17) | linker `FLASH LENGTH = 36K` |
| Application | `0x08009000` (page 18), at most 78 pages (pages 18..95) | `FWU_PLATFORM_IMAGE_MAX_PAGES` = 78; the application's own linker region is 156 KB. Pages 96..107 belong to the application's own data in the original product and must stay outside the update region |
| RAM | `0x20000000`, length `144K - 32` | the last 32 bytes (`0x20023FE0`) are the bootloader-to-application mailbox, `fwu_bootinfo_t`, magic `0x46574249` ("FWBI") |

The staging area, journal, counters and scratch pages follow from `src/config/layout_stm32g0b1.h` with the image limit applied by
`fwu_platform_boot_layout()`. The default of that header (110 application pages) differs from this example's 78: **the bootloader and the
application must use the same `fwu_platform.h`**, otherwise the contract fingerprint differs.

Profile and activation used: `FWU_PROFILE_DEV` (SHA-256 check, no signature, cannot be built with `FWU_PRODUCTION`), COPY activation. Product id 1001,
chunk size 256.

## Build settings used by the maintainer (STM32CubeIDE project, Debug configuration)

`-mcpu=cortex-m0plus -mthumb -mfloat-abi=soft -std=gnu11 -Os -ffunction-sections -fdata-sections -Wall -DUSE_HAL_DRIVER -DSTM32G0B1xx`, specs `nano.specs`.
The size of the maintainer's linked bootloader is not recorded in this repository; the compile check reports object sizes only.

## Known limitations

* Nothing calls `fwu_boot_info_check`: the application is expected to compare the mailbox contract with its own configuration, but no application code
  is provided here.
* The jump function resets the clock tree with `HAL_RCC_DeInit`; peripherals other than SysTick/NVIC are not reset.
* ECC/NMI behaviour: `boot_app_nmi` returns without reset only if the HAL status shows the ECC double-error flag; what the flash returns when a
  half-programmed double word is read after a power cut is an open question (`docs/KNOWN_ISSUES.md`, issue 41).
